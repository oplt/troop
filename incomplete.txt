### P0 — fix immediately

1. **CI is still red.** The latest Quality run failed. Backend installation now succeeds, which fixes the previous blocker, but Ruff fails; therefore Ruff-format, Alembic upgrade, migration smoke tests, workforce tests and the broader backend tests are all skipped. The frontend is now fully green: typecheck, lint, tests and production build all pass.

   The immediate task is simply to fix the Ruff violations and rerun CI. Do not weaken the lint configuration just to make it green. There are ordinary import-ordering, unused-import and simplification errors across workforce/orchestration code and tests.

2. **Workflow `human_input` currently has a logic bug and can loop forever.** `resume_run()` stores the submitted human input, but `_advance()` only considers an `approval` node satisfied when `approval_granted` is set. A `human_input` node therefore enters the pause branch again instead of completing and moving forward.

   Make separate durable completion conditions:

   ```text
   approval node
   → valid consumed ApprovalRequest

   human_input node
   → valid submitted HumanInput record/payload
   ```

3. **Tool approvals are server-owned now, but they are still too broad and reusable.** `_has_durable_tool_approval()` accepts `owner_id` but does not actually enforce it. It also does not bind approval to the exact normalized arguments/action fingerprint, and the approval is not consumed after execution. A general approved record for a run can potentially authorize repeated calls.

   Reuse the stronger semantics already present elsewhere in the orchestration engine:

   ```text
   ApprovalGrant
   - approval_request_id
   - owner_id
   - project_id
   - task_id
   - run_id
   - agent_id
   - action_key/tool
   - arguments_hash
   - approved_by
   - approved_at
   - consumed_at
   ```

   A grant should authorize **one exact action once**.

4. **Workflow approvals need the same hardening.** `resume_run()` now correctly rejects a raw `approval_granted=true`, which is good, but it only verifies an approved `ApprovalRequest`, optional project and optional `workflow_run_id`. It does not bind the approval to the current node/action or consume it.

   An approval for node A must never authorize node B.

5. **The actual TaskRun still does not snapshot SkillVersions.** Cursor improved the evaluation hook so it *can* receive `used_skill_version_ids`, but the real execution service does not appear to store or pass such a snapshot.

   This is one of the most important remaining architectural pieces. At run creation:

   ```text
   AgentSkillAssignment
       ↓ resolve pinned/latest
   exact SkillVersion IDs
       ↓
   freeze into TaskRun execution snapshot
   ```

   Then that exact snapshot should drive:

   * prompt construction
   * skill instructions
   * required tools
   * evaluation
   * audit trace

   If a skill publishes v4 while a run is executing v3, that run must remain on v3.

6. **Evaluation still produces misleading criterion-level scores.** At present every evaluation criterion gets `1.0` when the overall run succeeds and `0.0` when it fails.  That is not criterion measurement.

   Instead store:

   ```text
   criterion:
       status: measured | unmeasured
       score: null | numeric
       evaluator: deterministic | human | ai_judge
       evidence: [...]
   ```

   Do not infer “citation quality = 1.0” merely because the task completed.

7. **Evaluation errors are still effectively swallowed.** The hook accumulates errors and then ends with a `pass`.  Emit RunEvents/AuditEvents for evaluation failures and expose them in run diagnostics.

8. **Connector SSRF protection needs another pass.** The new validation is a substantial improvement, but there are some weaknesses. The scheme check currently produces the same `{http, https}` set regardless of `allow_http`, and ConnectorService calls the validator with `allow_http=True`.

   Production policy should be:

   * HTTPS by default.
   * HTTP only for explicitly enabled local/private development connectors.
   * validate every redirect target.
   * guard against DNS rebinding between validation and connection.
   * block cloud metadata/link-local/private networks by default.
   * preferably route MCP/A2A requests through Troop's managed external HTTP layer rather than raw unrestricted HTTP clients.

9. **Skill validation depends on `jsonschema`, but it is only a dev dependency.** Production publishing should not silently fall back to superficial “does this object contain a schema keyword?” validation when `jsonschema` is unavailable.

   Move `jsonschema` into normal runtime dependencies and distinguish:

   ```python
   ImportError
   ```

   from:

   ```python
   SchemaError
   ```

   Invalid JSON Schema must remain invalid.

### P1 — finish the core architecture

10. **WorkflowDefinition is still not the actual orchestration engine.** `WorkflowRuntimeService` still describes itself as a minimal runner. Agent, skill, tool, router, trigger and subworkflow nodes are recorded as `"delegated": true`; parallel only records children; delay completes immediately.

This should be the next major architectural task:

```text
WorkflowNode.agent
    → start/resume actual TaskRun

WorkflowNode.skill
    → resolve SkillVersion

WorkflowNode.tool
    → ToolRegistry.execute_tool()

WorkflowNode.approval
    → ApprovalRequest

WorkflowNode.parallel
    → real branches + join

WorkflowNode.subworkflow
    → child WorkflowRun

WorkflowNode.delay
    → Celery/durable schedule
```

Do not build another execution engine; connect WorkflowRuntime to the durable orchestration system that already exists.

11. **Generic execution is still GitHub-centric internally.** Manager/worker execution still hard-codes `github_sync`, `changed_files`, GitHub action state and `"Implementation bundle"`.

The generic runtime should only know:

```text
Artifact
Evidence
Decision
ToolCall
ExternalAction
Review
Result
```

Engineering workflows may then provide:

* changed files
* commit
* PR
* tests
* GitHub synchronization

as specializations.

12. **Task analysis context is improved but not complete.** It now includes project goals/description, department/company IDs and current skill/tool slugs.

It should additionally consider:

* actual department policies, not just department ID
* knowledge sources/documents
* connector installations
* ToolGrants
* ActionPolicies
* active SkillVersion capabilities/instructions metadata rather than only slugs
* project knowledge policy
* available agent capabilities

The analysis fingerprint should include versions/hashes of these dependencies. Right now changing a SkillVersion while keeping the same skill slug may not invalidate the cached analysis.

13. **There is a tool-filter inconsistency in TaskAnalyzer.** When structured `output_json` is returned, required tools are filtered against the available catalog. When the provider returns JSON as `output_text`, the code constructs `TaskAnalysisOutput` directly without that filtering.  Normalize both paths through exactly the same validation/filtering function.

14. **Provider routing is still heuristic rather than using Troop's actual routing engine.** The new resolver scores provider/model names using markers such as `mini`, `haiku`, `flash`, `opus`, `sonnet`, etc.

Replace this with the existing `ModelCapability`/routing system using:

* structured-output capability
* tool calling
* context size
* health
* cost
* latency
* configured fallback
* user/project model policy

Avoid maintaining two model-routing systems.

15. **Skill matching remains first-generation.** The current matcher has sensible hard scoping and capability/tool overlap, but `tasks.txt` correctly marks the deeper scoring as partial.

Add, in roughly this order:

* ToolGrant feasibility
* risk/approval compatibility
* input/output schema compatibility
* knowledge availability
* evaluation history
* semantic similarity
* cost/latency

Keep the score explainable.

16. **Agent matching remains too shallow.** It currently evaluates capability coverage, assigned skill coverage and tools.  Add:

* project membership
* department/project access
* effective ToolGrants
* knowledge access
* model capability
* current workload/availability
* past evaluation
* cost/latency
* autonomy/risk compatibility

Also batch the matched-skill lookup in `/agent-matches`; it currently resolves matched skills requirement-by-requirement.

17. **Composed-agent creation should validate executable permissions, not only declare tools.** The creation path now correctly adds SkillAssignments, project membership and provider configuration—good progress.  But an agent receiving:

```text
allowed_tools = ["fs_write"]
```

does not mean it actually has an effective ToolGrant/action-policy authorization for `fs_write`.

Before activation, calculate:

```text
requested tools
vs
effective permissions
```

and surface unresolved permission requirements.

18. **`ToolExecutionContext` should contain the run's SkillVersion snapshot.** Right now its `allowed_tools` are primarily taken from `AgentProfile.allowed_tools_json`.

It should resolve:

```text
run SkillVersions
    ↓ required tools

AgentProfile
    ↓ declared tools

ToolGrant
    ↓ actual permission

ActionPolicy
    ↓ autonomous / approval / prohibited
```

A SkillVersion can **request** a tool; it must never implicitly grant it.

19. **SkillVersion and SkillUsage frontend contracts are still stale.** Skill and SkillDraft are now handled much better, but the frontend `SkillVersion` still expects fields such as `snapshot_json` and `created_by_user_id`, while the backend returns the full version structure. The frontend `SkillUsage` expects `agent_count/task_count`, while the backend exposes run/success/acceptance/latency/cost/retry statistics.

Add:

* `normalizeSkillVersion`
* `normalizeSkillUsage`

and contract tests equivalent to the new Skill/SkillDraft tests.

20. **Department hierarchy needs cycle protection.** Parent departments are validated for existence in the same company, but there is no obvious prevention of:

```text
A → A
```

or:

```text
A → B → C → A
```

Add cycle detection before update.

21. **Department policy fields cannot reliably be cleared.** Several update checks use truthiness, so passing `{}` will not clear an existing policy.  Change them to explicit `is not None` semantics.

22. **The corrective SkillPack migration identifies uncertain ownership but doesn't fully resolve it.** The new ownership bridge is much safer than silently rewriting ownership and is a good migration audit trail.  But unresolved packs should not remain indefinitely as active skills under potentially incorrect owners.

Add one of:

* explicit organization/system-owned legacy skills, or
* `ownership_status=needs_reconciliation` + disable them until resolved.

Provide an admin reconciliation command/page if needed.

23. **Canonical Project/Task consolidation is still unfinished.** The tracker itself acknowledges the legacy `projects` and `project_tasks` models/tables remain for compatibility.

Once migration verification is green:

* identify all remaining callers
* migrate them
* drop legacy tables
* remove models/repositories
* eventually rename `OrchestratorProject` / `OrchestratorTask` to canonical `Project` / `Task`

24. **SkillPack retirement is also unfinished.** `SkillPack` remains readable for compatibility, and older template flows may still expose it.

Set a hard rule now:

> No new production path may write SkillPack or `skills_json`.

Then migrate the remaining reads and delete both once legacy data is safely converted.

25. **A true PostgreSQL end-to-end acceptance test is still missing.** The tracker explicitly states that the existing acceptance coverage is largely deterministic/contract-level rather than a full live HTTP workflow.

The most valuable test you can add now is:

```text
create organization
→ department
→ project
→ task
→ analyze
→ match skills
→ generate missing skill
→ validate
→ publish SkillVersion
→ create/assign agent
→ create run
→ freeze SkillVersion snapshot
→ execute low-risk tool
→ request approval for high-risk tool
→ human approves
→ consume approval
→ resume
→ produce artifact
→ complete
→ evaluate only used SkillVersions
```

Run this against actual PostgreSQL in CI.

### P2 — after the core above is stable

26. **MCP/A2A should remain beta for now.** The current tracker correctly downgraded them to `[~]`.  They now have actual connector execution rather than pure scaffolding, but production hardening should include:

* protocol negotiation/version compatibility
* session lifecycle
* retry/backoff
* circuit breakers
* connector health
* per-installation ToolGrants
* safe redirect/DNS handling
* secret rotation
* execution audit
* real test MCP/A2A servers in integration tests

The overall architecture is now in a good enough shape that I would **stop adding product features temporarily**. The next Cursor pass should focus almost entirely on:

> **green backend CI → exact one-time approvals → human-input fix → immutable SkillVersion run snapshots → accurate evaluation → real workflow-node execution → genericize the orchestration core → live PostgreSQL E2E → retire Project/Task and SkillPack duplication.**

Once those are done, Troop moves from “large set of promising workforce features” to a much more coherent **AI workforce runtime** where the same skills, permissions, workflow definitions and evaluation records actually govern execution end-to-end.
