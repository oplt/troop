I analyzed the current `main` branch after the Cursor work. The codebase is improved in several areas, but there are still clear **god-files** on both backend and frontend.

I used physical source lines from the current GitHub files. LOC is only one signal: `AgentProfilesPage.tsx`, for example, is just 341 lines but is ~29.5 KB because substantial JSX is compressed into very long lines.

### 1. `execution_service.py` — 3,390 LOC — highest priority

This is the strongest backend refactoring target.

It currently handles things such as:

* run retrieval
* child runs
* workflow definitions
* workflow/checkpoint state
* manager-worker subtask graphs
* worker-result normalization
* HITL grants
* review state
* artifact publication
* execution snapshots
* run events
* retry/resume behavior
* external actions
* reviewer decision parsing

These responsibilities are visible even in the first several hundred lines.

### Recommended structure

```text
backend/modules/orchestration/execution/
    execution_service.py          # thin public facade
    run_lifecycle.py              # create/start/fail/retry/resume
    run_queries.py                # list/get runs
    snapshots.py                  # task/run execution snapshots

    manager_worker/
        planner.py
        dispatcher.py
        result_contracts.py
        review.py

    hitl/
        grants.py
        approvals.py

    artifacts/
        publisher.py
        evidence.py

    external_actions.py

    execution_state.py            # existing
    execution_workflow.py         # existing
    policies.py                   # existing
```

**Important:** don't create another abstraction layer duplicating `execution_state.py`, `execution_workflow.py`, and `policies.py`. Move relevant code into those existing boundaries where appropriate.

Target:

```text
execution_service.py     ~200–350 LOC
individual modules       ~150–450 LOC
```

# Recommended implementation roadmap

### Phase 0 — Protect behavior first

Before splitting anything:

* add characterization tests around `execution_service`
* snapshot execution-state responses
* test retries/resume/HITL
* test manager-worker flows
* test task acceptance/status transitions
* test project settings normalization
* add component tests for AI Studio and admin forms

**Do not mix behavior changes with file-splitting commits.**

### Phase 1 — Frontend low-risk extraction

Do in this order:

1. `AdminPlatformPage`
2. `AiStudioPage`
3. `ActivityAuditPage`
4. `AdminSettingsPage`
5. `BrainstormDetailPage`
6. `AgentProfilesPage`

First extract components **without moving state**. Then move mutations/query hooks. This keeps diffs reviewable.

### Phase 2 — Backend pure/helper extraction

From the god-services first extract:

* normalization
* serializers
* result contracts
* validation
* settings merging
* acceptance/evidence calculation

These functions have fewer transactional side effects and are safest.

### Phase 3 — Split `tasks_service.py`

Extract:

```text
dependencies → acceptance → evidence → assignment → lifecycle → CRUD
```

Do lifecycle/status last because it carries the highest regression risk.

### Phase 4 — Split `projects/service.py`

Extract:

```text
portfolio
settings
team/hierarchy
workspace
memory
CRUD
```

Keep the existing service as a temporary facade.

### Phase 5 — Split `execution_service.py`

Do this last and incrementally:

```text
snapshots
    ↓
result contracts
    ↓
artifacts
    ↓
HITL
    ↓
external actions
    ↓
manager-worker planning
    ↓
run lifecycle
```

Do **not** rewrite the entire 3,390-line service at once.

### Phase 6 — AI + platform services

Split `AiService` and `PlatformService` by product domain after the critical orchestration code is stabilized.

## Target architecture

I would aim for these guidelines rather than enforce an arbitrary hard limit:

```text
React page/container       80–250 LOC
React feature component   100–300 LOC
React hook                 50–200 LOC

API/router                 100–300 LOC
business service          150–400 LOC
domain/policy module       80–300 LOC
repository                150–400 LOC
```

Files above ~500 LOC should trigger a design review; **1,000+ LOC business services should be exceptional**.
