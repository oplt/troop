# Troop Full-Stack and AI Architecture Remediation Report

**Repository:** `oplt/troop`
**Audit target:** current `main` plus recent refactor history
**Refactor commit reviewed:** `8246b13996bfe495d041cc4d28372bcd306fd162` — **“file shrinking”**, 14 August 2026
**Parent:** `60fcffbf3fa6d69d238fcdcd5596f36f1b4ab5f3`

## 1. Executive Summary

Troop already has a substantial architecture: FastAPI, asynchronous SQLAlchemy, PostgreSQL/pgvector, background ingestion, RAG, semantic/episodic/working memory, agent orchestration, approval flows, React 19, React Query, MUI, lazy-loaded routes, SSE/live updates and evaluation infrastructure. The project is considerably more mature than a basic agent dashboard.

The highest-value work now is **not adding more isolated features**. It is:

1. Establish backend ↔ frontend feature parity.
2. Fix several concrete API and performance problems.
3. Consolidate RAG and memory retrieval into predictable context-selection systems.
4. Reduce the number of UI surfaces a normal user has to understand.
5. Finish the architectural decomposition started by commit `8246b13`.
6. Add automated architectural checks so these problems do not return.

The most important confirmed findings are:

* `bulk_ingest_documents()` exists in the RAG router but **does not have a FastAPI route decorator**, while `docs/RAG_LAYER.md` says `/documents/bulk` exists. This is an actual backend bug/documentation drift.
* The dedicated RAG API supports project document CRUD, search, grounded answers, streaming answers and reindexing, but several of these capabilities are not represented in the frontend.
* AI Studio backend functionality is broader than its frontend API/client and UI. Missing or incompletely exposed capabilities include full run history/detail, dataset editing, creating evaluation cases from production traces and asynchronous runs.
* AI Studio polls the **entire `/ai/overview` every 2.5 seconds** while any document is ingesting, although only document status needs refreshing.
* `/ai/overview` itself sequentially fetches prompt templates, recent runs, all documents and datasets, making that polling particularly wasteful.
* AI evaluation cases currently execute sequentially. Large evaluation datasets therefore serialize expensive LLM calls.
* RAG already has useful caching and single-flight protection; the priority is therefore not “add Redis caching everywhere,” but improving retrieval quality and avoiding expensive fallback paths.
* Memory already has meaningful frontend coverage for project, company and task scopes. Task memory exposes working memory, coordination, episodic history and promoted semantic entries.
* The memory subsystem already parallelizes independent context retrieval and memory ingestion with separate sessions in important paths. Preserve this behavior rather than replacing it with generic `asyncio.gather()` calls.
* Commit `8246b13` was directionally correct and substantially reduced several god files, but it relies heavily on inheritance/mixin façades and leaves major concentration points such as `backend/modules/memory/service.py` and the orchestration router.
* The frontend already has persona-based navigation, collapsible groups, lazy loading and a command palette. UI simplification should build on that foundation rather than replacing it.

# 2. Target Architecture

The intended runtime flow should become:

```text
React UI
   │
   ▼
TanStack Query / typed API client
   │
   ▼
FastAPI route
   │
   ▼
Domain service
   │
   ├── Repository / PostgreSQL
   ├── pgvector
   ├── Redis/cache
   ├── worker/job queue
   └── external provider/tool
   │
   ▼
Domain event / SSE / cache invalidation
   │
   ▼
Targeted frontend query refresh
```

Agent execution should converge on one context pipeline:

```text
Task
 │
 ├── Working memory
 ├── Episodic recall
 ├── Semantic memory
 │     ├── task
 │     ├── project
 │     └── company
 ├── Procedural memory
 └── RAG knowledge
       ├── project documents
       ├── connected sources
       └── decisions
 │
 ▼
Retrieval planner
 │
 ├── scope
 ├── ranking
 ├── deduplication
 ├── authority
 ├── recency
 └── token budget
 │
 ▼
ContextPacket
 │
 ▼
LLM / Agent
 │
 ▼
Trace + outcome
 │
 ▼
Memory extraction / promotion / evaluation
```

Troop should have **one explicit context-selection policy**, rather than multiple retrieval mechanisms independently adding text to the prompt.

# Phase 2 — Bugs, Bottlenecks and Performance

**Focus:** reduce unnecessary DB/network/model work.

## P2.1 — Replace O(n) RAG document lookup — EASY

Current `get_rag_document()` loads a project document collection and finds the requested item with Python:

```python
rows = await OrchestrationService(db).list_documents(...)
row = next(...)
```

Replace with a repository query:

```python
get_document_for_project(project_id, document_id)
```

SQL should effectively become:

```sql
SELECT ...
FROM project_documents
WHERE id = :document_id
  AND project_id = :project_id
  AND deleted_at IS NULL
LIMIT 1;
```

---

## P2.2 — Stop polling the whole AI Studio overview — EASY

Current behavior:

```text
document pending
      ↓
GET /ai/overview every 2.5 sec
      ↓
providers
prompts
runs
all documents
datasets
```

Replace with:

```text
document pending
      ↓
poll GET /ai/documents/{id}
```

or preferably:

```text
ingestion worker
      ↓
SSE/event
      ↓
invalidate ["ai", "documents", id]
```

Keep the 2.5-second poll only as fallback.

---

## P2.3 — Parallelize independent AI overview queries — EASY

Current `get_overview()` awaits repository queries sequentially.

Independent read operations can be fetched concurrently **only if the database/session pattern safely permits it**.

Prefer an even better solution:

```text
AI Studio initial request:
    counts + recent summaries only

tab opened:
    fetch detailed tab data
```

Do not return complete document/dataset collections in a dashboard endpoint.

---

## P2.5 — Paginate unbounded collections — MEDIUM

Apply cursor pagination to high-growth entities:

```text

```

Do not rely on `limit=100` as the long-term pagination design.

## P2.6 — Parallelize evaluation execution safely — HARD

Current evaluation implementation:

```python
for case in cases:
    ai_run = await self.run_prompt(...)
```

So N cases ≈ N model calls sequentially.

Do **not** simply wrap this loop in:

```python
asyncio.gather(...)
```

because sharing one SQLAlchemy `AsyncSession` across concurrent operations is unsafe.

Preferred architecture:

```text
Evaluation run
   ↓
evaluation_run created
   ↓
N case jobs
   ├── independent DB session
   ├── provider call
   └── evaluation_run_item
   ↓
aggregation job
   ↓
scorecard
```

Use a configurable concurrency limit:

```text
AI_EVAL_CONCURRENCY=4
```

or provider-specific limits.

The memory worker already demonstrates the correct project pattern: concurrent jobs with **separate database sessions**.

---

## P2.7 — Define latency budgets — HARD

Recommended initial service objectives:

```text
Simple API read p95       < 250 ms
Project detail p95        < 500 ms
Vector retrieval p95      < 500 ms excluding embedding provider
UI navigation interaction < 100 ms local response
Initial page requests     minimize critical waterfall
```

Model generation should be reported separately rather than hidden inside ordinary API latency.

# Phase 3 — RAG Quality and Architecture

**Focus:** improve retrieval before adding more document sources.

Troop's current RAG implementation already contains useful foundations:

* pgvector retrieval;
* retrieval cache;
* single-flight cache filling;
* score threshold;
* project/task scoping;
* optional decision merge;
* Drive ACL filtering;
* redaction before indexing;
* citations;
* Python cosine fallback.

Do not rewrite it around LangChain merely for abstraction.

---

## P3.1 — Enforce context diversity and budget — EASY

Before sending chunks to an LLM:

```text
retrieve 20
 ↓
remove near duplicates
 ↓
cap chunks/source
 ↓
diversify
 ↓
fit token budget
 ↓
top context
```

Add:

```text
max_chunks_per_document
max_chunks_per_source
max_context_tokens
dedup_similarity_threshold
```

The current configuration describes a context budget, but selection should explicitly enforce it.

---

## P3.2 — Remove expensive production Python fallback — EASY/MEDIUM

The fallback loads candidate chunks and calculates cosine similarity in Python.

Keep this for:

```text
development
migration recovery
small installations
```

In mature production environments:

```text
pgvector unavailable
        ↓
metric + alert
        ↓
controlled degraded mode
```

rather than silently scanning a growing corpus.

---

## P3.3 — Add true hybrid retrieval — MEDIUM

Current primary search is vector-based, while the optional reranker only performs simple token overlap.

Add:

```text
vector search
     +
Postgres full-text search
     ↓
Reciprocal Rank Fusion
     ↓
candidate set
```

Example scoring:

```text
final_candidate_rank =
    RRF(vector_rank, lexical_rank)
```

This will help with:

* identifiers;
* names;
* product codes;
* task numbers;
* exact policy terminology;
* rare company vocabulary.

---

## P3.4 — Normalize decision ranking — MEDIUM

Current decision merge calculates lexical token-overlap scores and merges them directly with vector scores.

These values do not necessarily represent the same score distribution.

Instead use rank fusion:

```text
document vector rank
decision lexical rank
semantic memory rank
```

then:

```text
RRF / normalized rank
```

Do not directly compare heterogeneous raw scoring systems.

---

## P3.5 — Add second-stage reranking — MEDIUM/HARD

Current `RerankerService` is intentionally lightweight keyword overlap.

Upgrade the pipeline:

```text
retrieve top 30
 ↓
hybrid fusion
 ↓
rerank top 15
 ↓
select 5–8
```

Possible reranker implementations:

1. lexical lightweight mode;
2. cross-encoder/reranking provider;
3. LLM reranking for difficult/high-value requests.

Make it configurable.

Do not LLM-rerank every retrieval by default.

---

## P3.6 — Incremental document reindexing — HARD

Troop already computes content hashes during chunk construction/indexing.

Use those hashes to avoid embedding unchanged chunks.

On reindex:

```text
old chunk hashes
     vs
new chunk hashes

unchanged → keep embedding
changed   → regenerate
new       → generate
removed   → delete
```

This becomes important for GitHub, Drive and frequently changing enterprise documents.

---

Track:



## P4.2 — Show provenance everywhere — EASY

Every semantic memory card should be able to answer:

```text

Who/what created it?
Which task?
Which run?
Which document?
When?
Confidence?
Current or superseded?
```

The underlying model already stores provenance-related metadata and source identifiers.

Expose those values cleanly instead of presenting memories as unexplained text.

---

## P4.3 — Replace exact-content deduplication with semantic lifecycle — MEDIUM

Current memory-layer design includes content-hash deduplication.

Exact deduplication does not solve:

```text
"Project deadline is 10 September"

later:

"Project deadline moved to 18 September"
```

These are not duplicates.

Introduce:

```text
canonical_key
valid_from
valid_until
status
supersedes_memory_id
version
```

Example:

```text
canonical_key:
project/{id}/deadline
```

New authoritative memory:

```text
deadline = 18 September
```

should mark the old fact:

```text
superseded
```

rather than letting both compete during retrieval.

---

## P4.4 — Formalize promotion — MEDIUM

Use explicit progression:

```text
Run observation
    ↓
Task candidate
    ↓
Project memory
    ↓
Company memory
```

Not every execution detail deserves durable memory.

Recommended policy:

### Auto-promote

* stable task outcomes;
* approved decisions;
* verified constraints;
* explicit user preferences.

### Human approval

* company policy;
* security rules;
* legal/compliance instructions;
* high-impact cross-project facts.

### Never promote automatically

* transient logs;
* speculative agent reasoning;
* failed attempts;
* temporary tool errors.

---

## P4.5 — Consolidate context retrieval — HARD

`backend/modules/memory/service.py` currently handles multiple generations of memory/context behavior plus RAG integration and many lifecycle concerns.

Create a single:

```python
ContextRetrievalPlanner
```

responsible for:

```text
working
episodic
semantic
company
procedural
RAG
```

Return structured candidates:

```python
ContextCandidate(
    kind="semantic_memory",
    scope="project",
    content=...,
    relevance=...,
    authority=...,
    confidence=...,
    tokens=...,
    provenance=...,
)
```

Then one final selector handles:

```text
rank
deduplicate
conflicts
token budget
source quotas
```

This is preferable to every memory/RAG subsystem independently appending prompt text.

* virtualize only genuinely large lists;
* prefetch likely next destinations;
* use React Query cache intentionally;
* invalidate exact query keys instead of broad root keys;
* use SSE where state changes asynchronously instead of fixed polling.

The existing QueryClient already has nonzero stale time, 15-minute garbage collection and disabled automatic window-focus refresh.

# Phase 6 — Audit of Commit `8246b13` and Remaining Refactoring

**Focus:** verify whether “file shrinking” produced proper architectural boundaries.

## Overall conclusion

**The split was largely done in the correct direction, but it should be treated as the first architectural decomposition pass rather than the final state.**

The strongest changes include:

### AI

The previous AI service was split into:

```text
documents/
evaluations/
prompts/
providers/
retrieval/
reviews/
runs/
```

The current `AiService` is now a thin façade composing these concerns.

This is materially better than one large AI service.

### Execution

The large execution service was broken into:

```text
artifacts/
hitl/
manager_worker/
run_lifecycle/
run_queries
run_analytics
snapshots
tool_execution
external_actions
result_contracts
```

The current execution service is now primarily a composition façade.

This is a good domain split.

### Projects

Project logic moved into areas such as:

```text
project_crud
project_hierarchy
project_memory
project_settings
project_team_service
project_workspace
portfolio/
tasks/
```

The remaining `service.py` explicitly describes itself as a compatibility façade.

This is also directionally correct.

### Frontend

Large page components were moved into feature-oriented folders, while route pages such as AI Studio became thin loading/error boundaries.

That is preferable to keeping every form, mutation and display component in route-level files.

## Problems remaining after the split

### 1. Too much implicit mixin coupling

Examples:

```python
class AiService(
    AiPromptsMixin,
    AiDocumentsMixin,
    AiRetrievalMixin,
    AiRunsMixin,
    AiReviewsMixin,
    AiEvaluationsMixin,
):
```

and the execution/project façades follow a similar pattern.

Mixins solved file size but not all coupling.

A method inside one mixin can depend invisibly on:

```text
self.db
self.repo
self.ai_providers
methods supplied by another mixin
```

This makes dependency boundaries difficult to see.

---

## P6.1 — Document mixin dependencies — EASY

Until composition is introduced, each mixin should explicitly document:

```python
class AiRunsMixin:
    """
    Requires:
      self.db: AsyncSession
      self.repo: AiRepository
      self.providers: AiProviderRegistry

    Calls:
      self.retrieve_chunks(...)
    """
```

Add typing Protocols where practical.

---

## P6.2 — Add architecture/import tests — EASY

Add CI rules such as:

```text
domain repository must not import routers
domain services must not import frontend/API schemas unnecessarily
RAG cannot depend on route modules
memory cannot depend on HTTP layer
project domain cannot import workforce UI concepts
```

Use either:

* `import-linter`;
* custom AST tests;
* lightweight dependency graph validation.

Also fail CI on new circular imports.

---

## P6.3 — Remove compatibility shims gradually — MEDIUM

The refactor introduced compatibility façades intentionally.

Give them a removal plan:

```text
Phase A: all existing imports work
Phase B: migrate call sites to domain services
Phase C: emit/developer-mark deprecated imports
Phase D: delete compatibility shim
```

Do not maintain duplicate public APIs indefinitely.

## P6.5 — Split orchestration router by API domain — HARD

`backend/modules/orchestration/router.py` still imports and exposes a very broad collection of project, task, memory, execution, analytics, hierarchy and workflow concerns.

Target:

```text
orchestration/routers/
├── projects.py
├── tasks.py
├── runs.py
├── memory.py
├── providers.py
├── workflows.py
├── hierarchy.py

├── brainstorms.py
└── approvals.py
```

Then:

```python

```

This should be one of the final structural changes because router movement can generate a large noisy diff.

---

## P6.6 — Replace mixin inheritance with explicit composition — HARDEST

Long-term target:

```python
class AiService:
    def __init__(self, db):
        repo = AiRepository(db)

        self.prompts = PromptService(repo)
        self.documents = DocumentService(repo, ...)
        self.retrieval = RetrievalService(repo, ...)
        self.runs = RunService(
            repo=repo,
            retrieval=self.retrieval,
            providers=...
        )
        self.evaluations = EvaluationService(
            repo=repo,
            run_service=self.runs,
        )
```

Benefits:

```text
visible dependencies
simpler unit testing
less MRO complexity
fewer accidental cross-domain calls
better type checking
easier future service extraction
```

Do **not** convert every mixin in one PR.

Migrate one domain at a time.

# 8. Rules Codex Must Follow During Implementation

For every phase:

1. **Do not mix unrelated phases in the same commit.**
2. Preserve API compatibility unless the task explicitly removes a deprecated endpoint.
3. Before moving/refactoring logic, add characterization tests for current behavior.
4. Do not introduce concurrency using a shared SQLAlchemy `AsyncSession`.
5. Do not add a cache until the invalidation rule is defined.
6. Do not create a new frontend page when an existing entity detail page can own the feature.
7. Do not create a new React component solely to reduce LOC.
8. Do not introduce another vector database.
9. Keep PostgreSQL + pgvector as the canonical RAG/memory persistence layer unless benchmarks prove it insufficient.
10. Any memory retrieved across projects or company scope must pass explicit authorization and scope checks.
11. Any RAG/memory change must preserve provenance.
12. Every new asynchronous process must expose:

    * queued;
    * running;
    * completed;
    * failed;
    * retry/error state.
13. Every performance optimization must include before/after numbers.
14. Run targeted tests after each task rather than waiting until the entire phase is complete.

# 10. Definition of Done

The remediation is complete when:

### Backend/frontend parity

* every user-facing backend capability has an intentional UI surface;
* API-only/internal endpoints are explicitly classified;
* CI detects new parity drift.

### Performance

* AI Studio no longer polls a broad overview every 2.5 seconds;
* RAG document lookup is direct;
* large collections are paginated;
* evaluation datasets can execute with controlled concurrency;
* latency/query metrics exist.

### RAG

* retrieval combines semantic and lexical evidence;
* ranking systems use rank fusion rather than incomparable raw scores;
* context is deduplicated and token-budgeted;
* citations remain attached;
* incremental indexing avoids unnecessary embeddings;
* RAG regression tests exist.

### Memory

* task/project/company precedence is deterministic;
* stale facts can be superseded;
* provenance is visible;
* promotion rules are explicit;
* context selection is centralized;
* memory quality is measurable.

### Frontend

* normal users see only the small subset of navigation relevant to their persona;
* advanced capabilities remain reachable;
* project/task/agent details own related functionality;
* inspectors reduce unnecessary page transitions;
* AI Studio is reduced to Build/Test/Knowledge concepts.

### Architecture

* `8246b13`'s extracted domains remain intact;
* new god files are prevented;
* import boundaries are tested;
* `memory/service.py` and the main orchestration router are decomposed;
* mixin dependencies become explicit and are gradually replaced by composition.

# Final Assessment of the “File Shrinking” Commit

Commit **`8246b13` was a successful refactoring step**. It extracted meaningful domains rather than simply cutting files at arbitrary line boundaries. The AI, execution, project, task and platform splits largely follow coherent responsibilities, and the addition of characterization tests around execution/project/task behavior was particularly important.

However, the project should **not continue a strategy of “split every large file.”**

The next architectural objective should be:

> **reduce implicit coupling, not merely LOC.**

The highest-priority remaining structural targets are therefore:

```text
1. backend/modules/memory/service.py
2. backend/modules/orchestration/router.py
3. implicit service-mixin dependencies
4. API/UI contract drift
5. frontend information architecture
```

If those areas are addressed in the phased order above, Troop can move from a broad feature-rich agent application toward a substantially more maintainable enterprise automation platform without sacrificing the functionality already implemented.
